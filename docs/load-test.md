# 부하 측정 — 공급사 지연이 처리량 천장을 만드는가

design.md §5의 주장 — "MVC에서 타임아웃은 스레드 점유 시간의 상한이고, 공급사가 느려지면
죽는 건 공급사가 아니라 우리 쪽이다" — 을 숫자로 확인한 기록이다.

## 환경

- 로컬 단일 머신. 앱(8080)과 흉내 서버(9090)가 같은 장비 — **절대값이 아니라 구조를
  확인하는 측정**이다
- 앱은 `--server.tomcat.threads.max=20`으로 실행. 기본값 200이면 로컬 클라이언트 한계가
  먼저 와서 스레드 천장이 관측되지 않는다. 천장의 위치만 바뀔 뿐 구조는 같다
- 부하: 동시 클라이언트 40, 검색 API 반복 호출 (파이썬 스레드, 워밍업 후 측정)
- 흉내 서버의 `slow` 모드: 재고 조회에 2초 지연 후 정상 응답 (타임아웃 3초 미만이라 성공 처리)

## 결과

| 시나리오 | 처리량 | p50 | p95 | 실패 |
|---|---|---|---|---|
| 정상 (A·B 즉답) | **3,484 req/s** | 9ms | 24ms | 0 |
| A만 slow(2s), B 정상 | **9.9 req/s** | 4,020ms | 4,040ms | 0 |

같은 코드, 같은 스레드 20개 — 공급사 하나가 느려진 것만으로 처리량이 **352분의 1**이 됐다.

## 관찰 세 가지

**① 천장 = 스레드 수 ÷ 점유 시간, 정확히.**
20 스레드 ÷ 2초 = 예측 10 req/s, 실측 9.9 req/s. 요청 하나가 A의 응답을 기다리는 2초 동안
서블릿 스레드 하나를 점유하므로, 처리량은 트래픽이 아니라 이 나눗셈이 정한다.

**② 지연은 Little의 법칙대로 쌓인다.**
동시성 40 ÷ 처리량 10 = 4초. 실측 p50 = 4,020ms. 스레드(20)를 넘는 동시 요청(40)은 큐에서
한 바퀴(2초)를 더 기다린다 — 공급사 지연 2초가 사용자에게는 4초로 도착한다.

**③ 무관한 엔드포인트가 인질로 잡힌다.**
slow 부하가 도는 동안 `GET /internal/mappings`(공급사와 무관한 순수 DB 조회, 평소 1ms)를
찔러봤다:

```
평소:        1, 1, 1, 0, 0 ms
slow 부하 중: 2065, 2009, 2006, 2020, 2019 ms
```

같은 서블릿 풀을 쓰는 모든 요청이 공급사 지연의 볼모가 된다. "죽는 건 공급사가 아니라
우리 쪽"이라는 문장의 실체가 이것이다.

## 함의

- **타임아웃 값이 곧 천장의 분모다.** 공급사 호출 제한이 3초인 지금, 최악의 처리량 하한은
  스레드수 ÷ 3초다. 제한을 늘리면 천장이 그만큼 내려간다 — 3.5초 예산을 넉넉히 잡지 않은
  이유의 실측 근거
- 공급사 지연을 격리하려면 스레드-요청 결합을 끊어야 한다 — 전면 리액티브, 가상 스레드,
  또는 공급사 호출 전용 풀 분리. 지금 규모에서 도입하지 않은 근거와 조건은 design.md §5·§10
- 운영에서 이 상황을 알아채는 지표가 "공급사별 응답 지연"과 "스레드 풀 사용률"이다 —
  monitoring 설계의 1순위 입력

## 한계

- 로컬 측정이라 절대값(3,484 req/s)은 의미가 없다. 의미 있는 것은 두 시나리오의 구조적 차이와
  예측-실측 일치다
- 흉내 서버가 같은 머신이라 정상 모드 수치에는 상호 간섭이 있다
- 고정 응답이라 페이로드 크기·DB 조회량 변화는 반영되지 않았다
