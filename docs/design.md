# 설계 노트

두 개의 외부 숙박 공급사(이하 A, B)를 하나의 검색 API 뒤로 통합한다. 이 문서는 그 과정에서 내린
판단과, 각 판단이 무엇을 포기했는지를 기록한다. 코드를 읽기 전에 이 문서를 먼저 읽으면
"왜 이렇게 생겼는지"가 설명되도록 쓰는 것이 목표다.

> **읽는 법.** 본문은 *만들려는 시스템*을 현재형으로 기술한다. 결정이 먼저 서고 코드가 따라오는
> 순서로 작업하고 있어서, 어느 시점에는 문서가 코드보다 앞선다. 지금이 그렇다.
>
> | | 상태 |
> |---|---|
> | 표준 모델·포트 계약 (`domain`, `application/port`) | 있음 |
> | 설정 외부화 (`StayportProperties`, `application.yml`) | 있음 |
> | 매핑 엔티티·저장소·동기화 (`POST /internal/sync`) | 있음 |
> | 공급사 어댑터 — 숙소 목록, 재고·요금, 청크 분할 | 있음 |
> | 공급사 흉내 서버 (`mock` 프로파일, 9090) | 있음 |
> | 정규화·청크 분할 테스트 (흉내 서버를 실제 HTTP로 호출) | 있음 |
> | 통합 검색 API (병렬 호출·병합·부분 실패 응답) | 있음 |
> | ArchUnit 경계 테스트, 지표 계측 | 미구현 |
>
> 구현이 끝난 뒤 이 표를 지우고 문서와 코드를 한 번 대조한다. 대조에서 어긋난 것이 나오면
> 문서가 아니라 둘 중 틀린 쪽을 고친다.

## 1. 두 공급사가 같은 것을 다르게 말한다

A와 B는 같은 도메인을 다루지만 응답의 모양이 겹치지 않는다.

|  | Supplier A | Supplier B |
|---|---|---|
| 요금 단위 | 날짜별 1박 요금 | 기간 전체 총액 하나 |
| 세금 | `nightlyRate`(net)와 `taxAmount`가 분리 | 총액에 포함(`taxIncluded: true`)되고 금액은 미제공 |
| 재고 | 날짜별 잔여 객실 수 | 날짜별 잔여 객실 수 (같음) |
| 실패 통보 | HTTP 상태 코드 | 항상 HTTP 200, 본문 `resultCode` |
| 식별자 | `hotelCode` / `roomTypeCode` | `propertyId` / `roomId` |

이름이 다른 것은 어댑터에서 기계적으로 흡수하면 된다. 진짜 문제는 **정보의 양이 다르다**는 것이다.
A는 날짜별·세금별로 쪼갠 값을 주고 B는 뭉친 총액 하나만 준다. 통합 모델은 이 비대칭을 어느 쪽으로든
정리해야 한다.

## 2. 통합 모델 — 공통 분모는 총액, 나머지는 optional

`price.totalAmount`를 **숙박 기간 전체의 세금 포함(gross) 금액**으로 정의했다. 두 공급사 모두에서
계산 가능한 값이 이것뿐이기 때문이다. A는 각 날짜의 `nightlyRate + taxAmount`를 합산해서 만들고,
B는 `totalPrice`를 그대로 쓴다.

여기서 그냥 끝내면 A가 주는 날짜별 분해가 통째로 버려진다. 그래서 `price.dailyBreakdown`을
**선택 필드**로 남겼다. 값이 있으면 날짜별 gross를 보장하고, net·tax는 그것을 주는 공급사에서만
채워진다. B에서는 필드 자체가 null이다.

대신 클라이언트가 `dailyBreakdown`의 유무를 항상 확인해야 한다. 최소 공통 분모에 맞춰 A의 정보까지
버리면 계약은 더 단순해지는데, 요금 분해는 한 번 버리면 역산이 안 되는 정보라 보존을 택했다.
null을 허용하는 값에는 "있으면 이런 의미"를 타입과 문서로 붙여 둔다.

`taxAmount`를 표준 모델의 최상위 필드로 올리는 안도 검토했다가 뺐다. B에서 영원히 null인 필드를
계약의 1급 시민으로 만들면, 세금을 표시하는 클라이언트가 B 상품에서 조용히 0원을 그리게 된다.

### 재고 — 기간 전체 기준으로 접는다

두 공급사 모두 날짜별 잔여 객실 수를 준다. 검색 결과는 "이 조건으로 예약 가능한가"에 답해야 하므로
날짜별 값을 그대로 노출하지 않고 **기간 내 최솟값**으로 접어 `availableRooms`로 준다. 3박 중 하루가
0이면 그 상품은 예약할 수 없고, 이 규칙은 min으로만 표현된다.

`availableRooms == 0`인 상품도 응답에서 빼지 않는다. 뺄 경우 클라이언트는 "그런 객실이 없다"와
"있는데 만실이다"를 구분할 수 없다. 매진 표시 같은 UX 판단을 클라이언트에 넘기려면 재고 0도
사실대로 실어 보내야 한다.

### 조식은 상품 속성으로 남긴다

같은 숙소·같은 객실 타입이라도 A는 `breakfastIncluded: false`, B는 `true`인 경우가 실제로 있다.
이건 데이터 오류가 아니라 계약 조건의 차이다. 두 값을 병합하거나 한쪽으로 통일하면 가격 비교의
근거가 사라지므로 각 상품의 속성으로 그대로 둔다. 나중에 중복 숙소를 병합할 때도 이 필드가
"같은 상품인가"를 판단하는 재료가 된다.

## 3. 경계 — 공급사가 도메인으로 새지 않도록

```
api/            HTTP 요청·응답 (인바운드 어댑터)
domain/         표준 모델과 매핑. 공급사를 모른다
application/    유스케이스
  port/         SupplierAdapter 등 아웃바운드 포트
adapter/
  suppliera/    A 전용 DTO와 변환
  supplierb/    B 전용 DTO와 변환
  persistence/  매핑 저장소 구현
infra/          WebClient 구성, 설정 프로퍼티
mock/           공급사 흉내 서버 (mock 프로파일 전용)
```

포트 인터페이스를 어댑터가 아니라 `application` 안쪽에 둔 것이 핵심이다. "무엇이 필요한가"는
안쪽이 선언하고 "어떻게 얻는가"만 바깥쪽이 구현한다. 그래서 **새 공급사를 붙일 때 손대는 곳은
`SupplierAdapter` 구현체와 설정 두 곳뿐이고, 도메인과 API는 바뀌지 않는다.**

이 문장은 검증 가능해야 의미가 있다. 그래서 ArchUnit으로 아래 세 규칙을 걸 계획이다.

- `domain`은 `adapter`·`infra`·`api`를 참조하지 않는다
- 공급사 DTO 타입은 각자의 `adapter` 패키지 밖으로 나가지 않는다
- 어떤 패키지도 `mock`을 참조하지 않는다

설계 문서의 경계와 실제 코드는 시간이 지나면 대체로 어긋난다. 어긋났을 때 빌드가 깨지는 편이
문서를 다시 읽어 발견하는 것보다 낫다고 보고, 규칙을 테스트로 옮기기로 했다. 아직 안 썼다.

지금은 단일 배포다. 공급사 수나 트래픽이 늘면 어댑터부터 별도 모듈·별도 배포로 떼어낼 수 있도록
패키지 경계를 미리 그어 뒀다.

## 4. 매핑 — 저장하는 것과 저장하지 않는 것

이 애플리케이션이 DB에 넣는 것은 **공급사 코드 ↔ 내부 식별자 매핑뿐**이다. 재고와 요금은 저장하지
않고 매 요청마다 실시간으로 조회한다.

기준은 데이터의 성질이다. 숙소 목록은 거의 바뀌지 않고(정적), 재고·요금은 매 순간 바뀐다(휘발성).
휘발성 데이터를 저장하면 캐시 무효화 문제가 따라온다. 재고 오차의 비용이 커서, 저장하지 않는
쪽을 골랐다.

```
stay_mapping       (supplier, supplier_stay_code)                    → internal_stay_id
room_type_mapping  (supplier, supplier_stay_code, supplier_room_code) → internal_room_type_id
```

객실 타입 코드는 **숙소 안에서만 유일**하다. 다른 숙소에 같은 `DLX-TWN`이 존재할 수 있으므로
객실 매핑 키에는 숙소 코드가 반드시 함께 들어가야 한다. 이걸 놓치면 서로 다른 숙소의 객실이
같은 내부 ID를 갖게 되고, 증상은 검색 결과에서야 드러난다. 매핑을 구현할 때 회귀 테스트로
같이 고정할 항목이다.

두 테이블 모두 UNIQUE 제약을 걸어 "같은 공급사 상품은 항상 같은 내부 식별자"를 DB 수준에서
보장한다.

### 이름은 스냅샷으로 들고 있는다

응답의 `stayName`·`roomTypeName`은 재고 API 응답이 아니라 **매핑 테이블에 저장된 이름**을 쓴다.
두 API가 모두 이름을 주기 때문에 어느 쪽을 정본으로 삼을지 정해야 했다.

재고 API 쪽이 더 최신일 가능성은 있다. 그래도 매핑 쪽을 택한 이유는, 표시 값의 출처가 두 곳이면
같은 숙소가 요청 경로에 따라 다른 이름으로 보이는 상황이 생기기 때문이다. 이름 갱신은 동기화의
책임으로 몰아 경로를 하나로 만들었다. 대신 동기화 주기가 곧 이름의 신선도 상한이 된다.

### 동기화 시점과 동시성

기동 시 1회 자동 실행하고, `POST /internal/sync`로 수동 재실행할 수 있다. 주기 스케줄러는 넣지
않았다 — 목록이 정적인데 주기를 정할 근거가 없고, 근거 없는 주기는 나중에 아무도 못 바꾼다.

저장된 매핑은 `GET /internal/mappings`로 그대로 볼 수 있다. 매핑이 맞았는지 눈으로 확인할 창구가
하나는 있어야 하고, 같은 조회가 검색에서 코드 목록을 모을 때도 쓰인다.

동시 실행 문제는 락으로 풀지 않았다. **동기화 진입점을 하나로 만들고 이미 실행 중이면 즉시
반환**해서, 쓰는 주체가 항상 하나가 되도록 했다. UNIQUE 제약은 이 전제가 깨졌을 때의
안전망이고, 위반이 나면 재조회로 흡수한다.

이 구조는 **단일 인스턴스를 전제한다.** 여러 인스턴스가 뜨면 직렬화가 무효가 되고 UNIQUE 안전망만
남는다. 스케일아웃 시에는 동기화를 리더 인스턴스에 맡기거나 별도 배치로 분리해야 한다.

### 동기화가 실패하면

기동 시 동기화가 실패해도 **앱은 뜬다.** 공급사 한 곳의 장애로 서비스 전체가 기동하지 못하는 건
과한 결합이고, 기존 매핑이 이미 있으면 그것으로 계속 서비스할 수 있기 때문이다. 실패는 ERROR로
남기고 수동 재동기화로 복구한다.

첫 실행과 공급사 장애가 겹치면 매핑이 빈 상태가 된다. 이때 검색은 그 공급사를 부르지 않고
`NO_MAPPING`으로 표시한다(§7). "물어볼 게 없어서 결과가 없다"와 "물어봤는데 없다"는 원인이
다르고 클라이언트가 할 일도 다르다 — 전자는 재시도해도 같고, 후자는 잠시 후 달라질 수 있다.

## 5. 검색 흐름과 시간 예산

```
요청 검증
  → 매핑에서 공급사별 숙소 코드 수집
  → 공급사별로 50개씩 청크 분할
  → 코드가 있는 공급사만 골라 동시 호출 (Flux.flatMap)
  → 각 응답을 표준 모델로 정규화
  → 병합 (실패한 공급사는 빼고 계속)
  → 응답
```

### 왜 MVC인데 WebClient인가

전면 리액티브로 갈 만한 워크로드가 아니다. 검색 한 건이 부르는 외부 API는 공급사당 한두 번이고,
리액티브 전환은 스택 전체의 복잡도와 디버깅 비용을 함께 올린다. 반면 **두 공급사를 순차로 부르면
지연이 그대로 더해진다.** 그래서 외부 I/O 구간만 논블로킹으로 병렬화하고, 컨트롤러 경계에서
결과를 받아 동기 DTO로 돌려준다. 지연은 합이 아니라 최댓값이 된다.

요청 하나가 최대 3.5초 동안 서블릿 스레드 하나를 붙잡는 건 감수한다. 검토한 대안은
가상 스레드(Java 21)로 블로킹 호출을 그대로 두고 스레드 비용만 낮추는 방식이었는데, 이 경우
"두 공급사를 동시에 부른다"를 직접 조립해야 해서 병렬 구조가 오히려 덜 드러난다고 판단했다.

### 타임아웃 값

| 구간 | 값 | 근거 |
|---|---|---|
| TCP 연결 | 1s | 연결조차 안 되는 상대를 오래 기다릴 이유가 없다 |
| 공급사 호출 1회 | 3s | 아래 |
| 검색 API 전체 | 3.5s | 병렬이므로 max(3s) + 병합·직렬화 여유 0.5s |

공급사 호출은 Reactor의 `.timeout(3s)` **하나로만** 건다. read timeout을 따로 걸면 두 제한이
겹쳐서 어느 쪽이 발동했는지 로그에서 구분이 안 된다. 3초는 연결·응답·역직렬화를 전부 포함한 값이다.

값의 근거는 두 가지인데 성격이 다르다.

하나는 사용자 대기 시간이다. 검색이 3.5초를 넘기면 쓸 만한 응답이 아니라고 봤다. **다만 이건
측정한 값이 아니라 감이다.** 무응답 모드로 실제 경과 시간을 재보기 전까지는 임시값으로 둔다.

다른 하나는 용량이고, 이쪽은 논리로 따라온다. MVC에서 타임아웃은 곧 **스레드 점유 시간의 상한**이다.
길게 잡으면 공급사가 느려질 때 스레드 풀이 그만큼 오래 묶이고, 그 시점에 죽는 건 공급사가 아니라
우리 쪽이다.

이 값들은 전부 `application.yml`에 있다. 타임아웃은 운영하면서 조정될 게 뻔한 값이라 상수로
박아두면 바꿀 때마다 재배포해야 한다. 청크 크기, 공급사 주소, API 키도 같은 이유로 프로퍼티다.

**실측했다.** 흉내 서버를 30초 무응답으로 두고 검색을 부르면 3.0초 언저리에서 끊기고, 정상
응답일 때는 10ms대다. 양쪽 공급사를 모두 무응답으로 두어도 3.0초에 머문다 — 순차 호출이면
6초가 됐을 값이다. 병렬이 동작한다는 증거이자, 전체 예산 3.5초에 여유가 있다는 뜻이다.

여유가 큰 만큼 3.5초는 지금 데이터에 비해 넉넉한 값이다. 그래도 줄이지 않은 이유는 이 값의
근거가 측정이 아니라 계약이기 때문이다 — 공급사 호출 3초를 허용하기로 했으면 전체는 그보다
커야 하고, 병합·직렬화 여유 0.5초는 숙소 수가 늘면 실제로 필요해진다.

### 50개 제한과 그 너머

두 공급사 모두 한 번에 조회할 수 있는 숙소 코드가 50개다. 코드 목록을 50개 단위로 잘라 병렬로
부른다. 지금 데이터로는 1청크라 실제 분할이 일어나지 않는다. 그래서 오히려 경계가 안 밟힌다 —
흉내 서버가 51개를 거절하게 만들고 50·51개 케이스를 테스트로 고정해 뒀다. 나누지 않으면
테스트가 실패한다.

숙소가 수천 개가 되면 청크 수만큼 호출이 늘어 3.5초 예산 안에 못 들어온다. 그 지점에서는 실시간
전량 조회 자체를 포기해야 한다 — 공급사별 동시 호출 상한을 두고, 인기 숙소 위주로 사전 집계한
캐시를 앞단에 두는 쪽으로 간다. 지금 구조에서 그 전환의 접점은 "매핑에서 코드를 모으는" 단계
하나다.

## 6. 실패를 예외가 아니라 값으로

공급사 어댑터는 예외를 던지지 않고 `SupplierResult`를 돌려준다.

```java
sealed interface SupplierResult {
    record Success(SupplierId supplier, List<SupplierOffer> offers, int skippedItems) ...
    record Partial(SupplierId supplier, List<SupplierOffer> offers, int skippedItems,
                   int failedChunks, Map<FailureType, Integer> failures) ...
    record Failure(SupplierId supplier, FailureType type, String detail) ...
}
```

부분 실패를 허용한다는 건 "한쪽이 실패해도 나머지로 응답한다"인데, 실패가 예외로 올라오면 호출부는
try-catch로 흐름을 끊어야 한다. 값으로 받으면 병합 단계에서 성공만 골라 담는 것으로 끝난다.
`onErrorResume`으로 어댑터 안에서 모든 오류를 `Failure`로 접는 이유다.

세 갈래는 응답 계약의 `OK | PARTIAL | FAILED`와 일대일로 대응한다(§7). 상태를 문서에만 정의해
두면 코드에서 그 상태가 어디서 생기는지 흐려지므로, 타입이 계약을 그대로 비추게 했다.

### 실패 요약은 호출 순서에 의존하지 않아야 한다

`Partial`은 실패를 하나로 줄이지 않고 **유형별 개수**를 담는다. 청크는 병렬로 나가고 끝나는
순서가 매번 다르기 때문에, 요약을 "먼저 끝난 실패"로 정하면 같은 요청이 실행마다 다른 분류를
내놓는다. 그러면 클라이언트의 재시도 판단이 비결정적이 된다.

하나로 줄여야 하는 자리(모든 청크가 실패해 `Failure`가 될 때)에서는 `FailureType`의 선언
순서를 우선순위로 쓴다. 기준은 **재시도해도 달라지지 않는 것을 먼저 알린다**다 —
`AUTH`·`INVALID_REQUEST`·`PARSE_ERROR`가 `RATE_LIMIT`·`SUPPLIER_ERROR`·`TIMEOUT`보다 앞선다.
"타임아웃 3건과 인증 실패 1건"을 "타임아웃"으로 요약하면, 정작 우리가 고쳐야 할 인증 문제가
일시적 장애로 읽힌다.

### 어댑터가 내놓는 것은 아직 공급사 코드다

`Success`가 담는 것은 `StayOffer`(내부 식별자를 가진 최종 형태)가 아니라 `SupplierOffer`다.
**어댑터는 매핑을 모른다.** 어댑터에 매핑을 넘겨주면 공급사 연동 계층이 우리 저장소에 의존하게
된다. 그래서 어댑터는 정규화(요금 합산, 재고 min, 조식 보존)까지 끝내고 공급사 코드 기준으로
반환하고, 유스케이스가 내부 식별자로 변환해 최종 응답을 만든다.

이 변환 지점에서 숙소명도 매핑 스냅샷으로 바뀐다(§4). 어댑터가 준 이름은 표시에 쓰지 않는다.

### 판정 통일

A와 B는 실패를 알리는 방식이 다르다.

- A: HTTP 4xx/5xx → 실패
- B: **HTTP 200이어도 `resultCode != "0000"`이면 실패**

B의 `resultCode`를 확인하지 않으면 장애 응답의 `data: null`이 "결과 0건"으로 처리된다.
"방이 없다"와 "공급사가 죽었다"는 클라이언트에게 다른 사실이다. 판정은 각 어댑터가 하고,
밖으로는 `FailureType` 하나의 축으로만 내보낸다.

`INVALID_REQUEST / AUTH / RATE_LIMIT / SUPPLIER_ERROR / TIMEOUT / PARSE_ERROR`.
A의 429와 B의 `E429`가 같은 값으로 접히는 식이다. 재시도 판단은 이 분류만 보면 되게 했다.

### 깨진 응답의 격리 범위

파싱 실패를 어느 단위로 격리할지도 정해야 했다.

- 응답 전체가 우리가 아는 형태가 아니면 → 그 공급사를 `Failure(PARSE_ERROR)`
- 목록 중 개별 상품 하나가 이상하면 → **그 건만 건너뛰고** WARN, 나머지는 정상 반환

상품 하나 때문에 공급사 전체를 버리는 건 과하다. 다만 아무 표시 없이 버리면 데이터 손실을
알 수 없으므로, 건너뛴 수를 세어 `skippedItems`로 응답에 노출한다.

같은 응답 안에 같은 `(숙소, 객실)`이 두 번 오는 경우도 여기에 포함된다 — 규약 이상이므로
첫 건만 채택하고 나머지는 스킵으로 센다. 값이 다른 두 건 중 어느 쪽이 옳은지 알 방법이
없어서, 결정적인 규칙(첫 건) 하나를 정해 두는 쪽을 택했다. 매핑에 없는 숙소가 응답에 온
경우도 마찬가지로 스킵 계수에 잡힌다 — 내부 식별자를 만들어 낼 수 없기 때문이다.

## 7. 응답 계약

```
GET /api/v1/stays/search?checkIn=2026-09-01&checkOut=2026-09-04&adults=2&children=0
```

응답에는 상품 목록과 함께 **공급사별 상태**가 실린다.

B가 죽은 상황의 실제 응답이다 (필드 전부, 값은 예시 데이터 기준):

```json
{
  "checkIn": "2026-09-01",
  "checkOut": "2026-09-04",
  "nights": 3,
  "adults": 2,
  "children": 0,
  "stays": [
    {
      "stayId": 2, "stayName": "Riverside Hotel Seoul",
      "roomTypeId": 2, "roomTypeName": "Deluxe Twin",
      "maxOccupancy": 2, "availableRooms": 1, "bookable": true,
      "breakfastIncluded": false, "supplier": "A",
      "price": {
        "totalAmount": 429000, "currency": "KRW",
        "dailyBreakdown": [
          { "date": "2026-09-01", "grossAmount": 132000, "netAmount": 120000, "taxAmount": 12000 }
        ]
      }
    }
  ],
  "suppliers": [
    { "supplier": "A", "status": "OK", "returnedOffers": 2,
      "skippedItems": 0, "failedChunks": 0, "failures": {} },
    { "supplier": "B", "status": "FAILED", "returnedOffers": 0,
      "skippedItems": 0, "failedChunks": 0, "failures": { "SUPPLIER_ERROR": 1 } }
  ]
}
```

`status`는 `OK | PARTIAL | FAILED | NO_MAPPING`이다.

- `PARTIAL` — 나눠 부른 것 중 일부만 실패. 성공한 묶음의 결과는 반환하면서 실패 사실을 함께 알린다
- `NO_MAPPING` — 매핑이 없어 부르지 않았다. 공급사 장애와 원인이 다르므로 `FAILED`와 나눈다(§4).
  이 상태는 어댑터를 거치지 않으므로 `SupplierResult`의 세 갈래(§6) 밖에서, 유스케이스가
  호출 전에 만들어 붙인다
- `failures` — 실패 유형별 개수. 하나로 요약하지 않는다
- `skippedItems` — 형태가 깨졌거나 매핑이 없어 버린 상품 수. 결과가 적은 이유가 재고인지
  우리 쪽 문제인지 구분하는 근거

요금 필드가 A와 B에서 어떻게 다른지: A는 `dailyBreakdown`에 날짜별 gross/net/tax가 차고,
B는 `dailyBreakdown: null`에 `totalAmount`만 있다.

### HTTP 상태 코드

**요청 검증 실패만 400이고, 나머지는 전부 200이다.** 400의 본문은 실패 지점과 무관하게
`{error, message}` 한 가지다 — 파라미터 누락·형식 오류(바인딩 단계)와 값 검증 실패(도메인)가
스프링 기본값처럼 서로 다른 스키마로 나가면 클라이언트가 둘 다 파싱해야 한다. 두 공급사가 모두 죽어도
`200 + suppliers: [FAILED, FAILED]`를 준다.

아무것도 못 가져왔는데 200을 주는 게 맞느냐는 반론이 가능하다. 그래도 200인 이유는 이 API의
실패가 **공급사 단위로 부분적**이기 때문이다. 응답 전체를 5xx로 만들면 "A는 성공했고 B만
죽었다"를 표현할 방법이 없다.

재시도 판단도 마찬가지다. 클라이언트는 응답 전체가 아니라 `suppliers[].status`를 보고 어느 공급사를
다시 부를지 정해야 한다. 상태 코드를 그 판단의 근거로 삼게 하면 전부 아니면 전무가 된다.

전량 실패를 별도로 알려야 한다면 상태 코드가 아니라 응답 본문의 요약 필드로 다루는 게 이 계약과
일관된다.

## 8. 지금 전제하고 있는 것

설계가 성립하기 위해 기대고 있는 조건들이다. 깨지면 다시 봐야 한다.

- **단일 인스턴스.** 동기화 직렬화가 여기에 걸려 있다(§4).
- **내부 식별자를 그대로 노출한다.** DB의 auto-increment Long이 응답에 나간다. 실무라면 내부 PK와
  공개 식별자를 분리해 순번 노출과 열거를 막아야 하지만, 지금은 분리에서 얻는 것보다 계층이 하나
  느는 비용이 커 보였다. 운영 전환 시 ULID 등으로 공개 식별자를 따로 두는 것이 다음 단계다.
- **숙소 수가 수백 규모.** 실시간 전량 조회는 여기까지만 유효하다(§5).
- **서로 다른 공급사의 같은 숙소는 각자 다른 내부 ID를 갖는다.** A의 숙소와 B의 숙소가 실제로 같은
  건물이어도 지금은 별개 상품으로 노출된다. 공통 키가 없어 이름·좌표 유사도로 추정해야 하는데,
  잘못 병합하면 가격이 섞여 보이는 사고가 난다. 자동 병합 대신 후보만 저장하는 방향을 별도 문서로
  다룬다.
- **통화가 섞이지 않는다.** 두 공급사 모두 `currency`를 주지만 지금 데이터는 KRW뿐이라 통화 간
  비교·정렬은 다루지 않았다. 해외 숙소를 붙이면 이 가정이 가장 먼저 깨진다.

## 9. 관측 — 지금 정해둔 것

지표와 대시보드 설계는 별도 문서로 뺀다. 여기서는 그 문서가 기댈 자리를 타입 단계에서 미리
만들어 뒀다는 것만 적는다. 계측 코드는 아직 없다.

- 실패가 `FailureType`으로 분류되어 있으므로 나중에 "타임아웃이 늘었는가"와 "공급사가 500을
  뱉는가"를 따로 셀 수 있다. 두 상황은 대응이 달라서 한 카운터에 섞이면 곤란하다.
- `Success.skippedItems`가 조용한 손실을 셀 자리다. 지표로 올리는 건 어댑터를 만든 뒤다.
- 로깅 정책은 실패 시에만 WARN + 요약(공급사·상태·소요 시간), 본문은 DEBUG로 가기로 했다.
  요청마다 본문을 통째로 남기면 처리량이 눈에 띄게 깎인다.
