# AI 활용 기록

7일 동안 AI를 어디에 썼고 그 답을 어떻게 다뤘는지 적은 기록입니다. AI는 구현 속도와 반대
심문에 썼고 결정은 제가 했습니다. 아래는 그 주장을 확인할 수 있는 구체적인 자국들입니다.

## 역할을 둘로 나눈 이유

| 도구 | 맡긴 일 |
|---|---|
| Claude (Claude Code) | 구현 초안, 리팩터링, 테스트 작성, 문서 초안, 도해 |
| Codex | 반대 심문 — 코드 리뷰, 문장 리뷰, 주장-코드 대조 |

같은 모델에게 짜게 하고 검사까지 시키면 자기 결과를 변호합니다. 실제로 작성자 쪽 모델은
"의도대로 동작한다"는 설명을 붙였고, 검사자 쪽 모델은 같은 코드에서 결함을 찾아냈습니다.
그래서 사람 리뷰어를 한 명 더 두듯 둘로 나눴습니다.

## 질문과 답의 처리

**받아들인 것**

| 지적 | 조치 |
|---|---|
| `collectList().timeout(예산)`은 한 공급사가 늦으면 **이미 받은 다른 공급사 결과까지 버린다** | `take(예산)` + 미응답 공급사는 차집합으로 TIMEOUT 채우기. 부분 실패 허용의 핵심이 무너질 뻔한 자리라 회귀 테스트를 함께 넣었습니다 |
| 2xx인데 본문이 비면 "재고 0건"으로 둔갑한다 | 4개 경로에 `switchIfEmpty` → `PARSE_ERROR`, 흉내 서버에 `empty-body` 모드 추가 |
| "첫 실패의 분류를 남긴다"는 병렬 완료 순서에 의존해 비결정적이다 | 유형별 개수를 보존하고 `FailureType` 선언 순서를 우선순위로. 순서 무관성 자체를 테스트로 고정 |
| 매핑 색인 키를 문자열 연결로 만들면 코드에 구분자가 들어올 때 서로 다른 튜플이 한 키로 합쳐진다 | 레코드 키 + `putIfAbsent` 충돌 시 즉시 예외 |
| 설계 문서의 응답 예시가 실제 직렬화 형태와 다르다 | 실제로 찍어 본 응답으로 교체 |
| 타임아웃 예산이 서로 모순(공급사 3초인데 전체도 3초) | 전체 예산을 3.5초로 — 병합·직렬화 여유 |

근거를 고쳐서 받아들인 것도 있습니다.

- Kotlin을 권했고 근거는 "팀 스택 추정"이었습니다. 언어 선택은 남겨 두되 근거를 "제가
  설명할 수 있는 코드를 쓴다"로 바꿨습니다. Java 21을 골랐습니다.
- 도해 문구를 처음엔 압축된 명사구("형식·실패 방식 흡수")로 받았습니다. 처음 보는 사람이
  한 번 더 해석해야 해서 풀어 쓴 문장으로 바꿨습니다.

**거부한 것**

- ONNX 임베딩으로 중복 숙소를 매칭하자는 제안. 선택 항목 하나 때문에 모델 패키징·
  토크나이저·로딩 실패 처리·임계값 검증이 따라옵니다. 7일 안에 안정화할 수 없고, 무엇보다
  이 저장소를 받은 사람이 그대로 돌릴 수 없게 됩니다. 이름 정규화와 객실 구성 비교로
  후보만 찾는 방식으로 대체했습니다(`GET /internal/duplicates`).
- 메시지 브로커·캐시·컨테이너 추가. 공급사가 변경 피드를 주지 않아 폴링 구조라 흐를
  데이터가 없습니다. 도입 조건은 design.md §10·§11에 적고 코드에는 넣지 않았습니다.
- **첫 리뷰의 지적 5건**: 아래에 따로 적었습니다.

## 질문을 좁히니 오탐이 사라졌습니다

1일차에는 공급사 명세를 주지 않고 "설계를 리뷰해 달라"고 열어서 물었습니다. 지적 7건 중
5건이 **오탐**이었습니다. 명세에 없는 요금제(RatePlan) 개념, B가 주지도 않는 날짜별 재고,
쓰지 않는 페이징처럼 모델이 일반적인 숙박 도메인 지식으로 빈칸을 메운 결과였습니다.

3일차부터 질문을 **"이 주장이 코드에서 사실인지 대조하라"**로 바꾸고 대상 파일을 같이
줬습니다. 통합 검색 리뷰에서 나온 지적 7건은 전부 실제 결함이었습니다(오탐 0).

같은 도구인데 결과가 달랐습니다.

리뷰가 유용하려면 모델이 추측할 여지를 없애야 한다는 것을 이때 알았고, 이후 리뷰는 전부
대상과 근거를 지정해서 요청했습니다.

## 지적을 검증한 방법

지적을 그대로 믿지 않으려고 두 가지를 했습니다.

고친 코드를 원래대로 되돌려 봤습니다. `take(예산)` 수정이 진짜 필요한 것인지 확인하려는
것이었습니다. 테스트를 돌리니 새로 넣은 7개 중 5개가 빨간불이 됐고 그제야 수정을
복원했습니다. 테스트가 지적을 재현하지 못하면 그 지적은 제 코드에 대한 것이 아닙니다.

**문서-코드 대조.** 마지막 날 리뷰에서 "`monitoring.md`가 설명하는 지표와 실제 기록 지점이
다르다"는 지적을 받았습니다. 문서가 코드보다 앞서 나간 자리였고, 같은 종류의 어긋남을
design.md §9에서도 발견했습니다(계측을 구현한 뒤에도 "아직 없다"고 적혀 있었습니다).
코드를 못 따라가는 문서는 거짓말이 되므로 발견한 자리를 고쳤습니다.

## AI가 쓴 문장을 걷어낸 작업

4일차에 문장만 따로 리뷰를 받았더니 "상당 부분이 AI가 쓴 것으로 읽힌다"는 판정이
나왔습니다. 격언조 마무리, 문단 구조의 균일함, 파일 간에 똑같이 반복되는 근거를 들었습니다.

- Javadoc 393줄 → 205줄. 동기·비유·반례까지 담던 에세이형 주석을 계약과 불변식만 남기고
  줄였습니다. 근거 산문은 design.md 한 곳으로 모았습니다.
- 커밋 본문도 같은 기준으로 줄였습니다. 판단이 담긴 것만 길게 두고 나머지는 한두 줄로.
- 작업 기록(JOURNAL)은 날짜별 사실을 따로 모아두고 제 문장으로 고쳐 씁니다. 여기까지
  매끄럽게 다듬으면 같은 문체가 다시 남고, 무엇보다 인터뷰에서 제 목소리로 말할 수
  있어야 합니다.

리뷰가 지적한 문장이라도 판단이 담긴 것은 남겼습니다. 제가 설명할 수 있는 문장만 남기는
것이 목표였습니다.

## 남아 있는 것

- 리뷰는 두 모델의 판단이라 사람 리뷰어가 잡을 만한 것(도메인 관행, 팀 컨벤션)은 그대로
  남아 있을 수 있습니다.
- 마지막 리뷰에서는 구조 개선 지적도 몇 가지 나왔습니다. 어댑터 간 중복 코드, 파생 가능한
  상태를 두 곳에서 유지하는 것 같은 자리인데, 남은 시간과 회귀 위험을 견주어 이번에는
  반영하지 않았습니다. 무엇이 남았는지는 알고 있습니다.
