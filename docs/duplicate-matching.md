# 중복 숙소 — 합치지 않고, 찾아는 둡니다

두 공급사가 같은 건물을 각자의 코드로 팝니다. 합칠지 따로 노출할지에 대한 판단과 그 구현을
적습니다. 결론은 **따로 노출하되, 같은 숙소로 보이는 쌍은 찾아서 보여준다**입니다.

## 문제 — 공통 키가 없습니다

식별자는 공급사마다 자기 체계로 부여합니다. A의 `A-10023`과 B의 `B77120`이 실제로 같은
호텔이어도, 그 사실을 알려주는 공통 키는 어디에도 없습니다. 동일 숙소 여부는 숙소명이나 객실
구성 같은 **간접 증거로 추정**하는 수밖에 없습니다.

흉내 서버 데이터에 이 상황을 그대로 심어 뒀습니다.

| | Supplier A | Supplier B |
|---|---|---|
| 코드 | `A-10023` | `B77120` |
| 숙소명 | Riverside Hotel Seoul | Riverside Hotel Seoul |
| 객실 | Deluxe Twin (2인) | Deluxe Twin Room (2인) |
| 3박 총액 | 429,000원 | 452,000원 |
| 조식 | 없음 | **포함** |

## 판단 — 합치지 않습니다

**① 값이 싼 쪽이 이긴 것이 아닙니다.** 429,000원과 452,000원을 나란히 두고 싼 쪽만 남기면
조식이 사라집니다. 23,000원 차이가 조식값이라면 B가 더 나은 상품일 수도 있고, 그 판단은
고객이 할 몫입니다. 병합은 필연적으로 **어느 쪽을 대표로 삼을지**를 정해야 하는데, 조건이
다른 두 상품 사이에서 그 기준을 시스템이 대신 정할 근거가 없습니다.

**② 조식 말고도 숨은 차이가 더 있을 수 있습니다.** 취소 정책, 결제 조건, 어메니티는 지금
스펙에 아예 없는 필드입니다. 지금 보이는 정보만으로 "같은 상품"이라고 선언하면, 나중에 필드가
늘어날 때 이미 합쳐 버린 것을 되돌려야 합니다. **합치는 것은 정보를 버리는 방향이라 되돌리기가
어렵고, 따로 두는 것은 나중에 합치기가 쉽습니다.**

**③ 추정이 틀릴 수 있습니다.** 이름과 객실 구성은 간접 증거입니다. 체인 호텔의 지점명이
비슷하거나 리브랜딩 직후라면 오판이 납니다. 오판의 대가가 비대칭입니다 — 따로 노출했는데
사실 같은 숙소였다면 목록에 두 번 나올 뿐이지만, 합쳤는데 다른 숙소였다면 **고객이 예약한
곳과 다른 건물로 갑니다.**

**④ 필수 계약을 어기지 않습니다.** 반드시 지켜야 하는 것은 "같은 공급사 상품이 항상 같은
내부 식별자로 돌아오는 것"이지, 서로 다른 공급사의 상품을 한 식별자로 묶는 것이 아닙니다.
공급사가 다르면 내부 식별자도 다른 것이 기본 동작입니다.

그래서 검색 응답에서 이 둘은 **서로 다른 `stayId`로 두 번** 나옵니다. `supplier` 필드와
`breakfastIncluded`가 함께 나가므로 클라이언트는 무엇이 다른지 볼 수 있습니다.

## 그럼에도 탐지는 합니다

합치지 않는다는 것과 모른 척한다는 것은 다릅니다. 같은 숙소가 목록에 두 번 나오는 것은
운영에서 알고 있어야 할 사실입니다 — 정산 대상이 겹치는지, 한쪽 공급사와의 계약이 무의미해진
것은 아닌지 판단하려면 후보 목록이 있어야 합니다.

`GET /internal/duplicates`가 그 목록입니다. 자동으로 아무것도 바꾸지 않고, 판정 근거와 함께
후보만 보여줍니다.

```json
[
  {
    "first":  { "supplier": "B", "supplierStayCode": "B77120", "internalStayId": 1, "stayName": "Riverside Hotel Seoul" },
    "second": { "supplier": "A", "supplierStayCode": "A-10023", "internalStayId": 2, "stayName": "Riverside Hotel Seoul" },
    "nameSimilarity": 1.0,
    "roomMatchRatio": 1.0
  }
]
```

## 어떻게 찾는가

`DuplicateCandidateService`가 저장된 매핑만 읽어 계산합니다. 공급사를 부르지 않으므로 검색
경로의 시간 예산과 무관합니다.

1. 매핑(객실 단위)을 숙소 단위로 접어 `(공급사, 숙소 코드, 숙소명, 객실 목록)` 프로필을 만듭니다.
2. **서로 다른 공급사**의 프로필끼리만 비교합니다. 같은 공급사 안에서는 코드가 이미 유일합니다.
3. **숙소명**을 소문자로 낮추고 문자·숫자가 아닌 것으로 잘라 토큰 집합을 만든 뒤 자카드 유사도를
   봅니다. `0.6` 미만이면 후보가 아닙니다.
4. **객실 구성**을 봅니다. 최대 수용 인원이 같고 객실명 토큰이 절반 이상 겹치면 짝으로 봅니다.
   짝을 찾은 객실 수를 **적은 쪽 객실 수**로 나눠 일치율을 냅니다. `0.5` 미만이면 후보가 아닙니다.

"Deluxe Twin"과 "Deluxe Twin Room"이 짝으로 잡히는 것이 3번·4번을 나눈 이유입니다. 이름만
보면 다르고, 인원과 함께 보면 같은 방입니다.

임계값 두 개를 다 넘어야 후보가 됩니다. 이름만 비슷한 체인 호텔과 객실 구성만 우연히 같은
숙소를 각각 걸러내기 위해서입니다.

## 합친다면 — 어떤 조건에서

지금 합치지 않는 이유가 사라지는 조건이 있습니다.

- **공급사가 공통 식별자를 주게 되면**(체인 코드, GIAT/GDS 코드 등) 추정이 사실로 바뀝니다.
  그때는 탐지가 아니라 매핑 테이블에 열 하나가 늘어나는 문제가 됩니다.
- **비교에 필요한 조건이 모두 필드로 들어오면**(조식·취소 정책·결제 조건) "같은 조건의 같은
  방"을 정의할 수 있게 됩니다. 그때의 병합 단위는 숙소가 아니라 **조건이 같은 객실 상품**이고,
  응답은 대표 상품 하나에 `otherOffers[]`를 다는 형태가 됩니다 — 정보를 버리지 않는 병합입니다.
- **운영자가 확정한 쌍**만 병합하는 방법도 있습니다. 지금 구조에서 가장 가까운 경로입니다.
  `/internal/duplicates`가 후보를 내고, 사람이 확인한 것만 별칭 테이블에 넣고, 검색이 그
  테이블을 보고 묶는 식입니다. 자동 판정과 달리 오판의 책임 소재가 분명합니다.

셋 중 무엇이든 **사람이나 공급사가 확인해 준 사실**이 먼저 있고 병합은 그다음입니다. 추정만으로
합치는 단계는 건너뜁니다.

## 한계

- 임계값 `0.6`·`0.5`는 실제 숙소명 분포를 보고 정한 값이 아닙니다. 한국어·영어가 섞인 이름에서
  자카드가 어떻게 분포하는지 재본 적이 없어서, 지금은 예시 데이터에서 동작하는 값입니다.
  운영이라면 `application.yml`로 빼서 조정할 값입니다.
- 객실 일치율의 임계값(`0.5`)이 **객실명 유사도와 전체 일치율 양쪽에 같이 쓰입니다.** 사실
  서로 다른 두 개의 손잡이인데 하나로 붙어 있습니다.
- 토큰 자카드는 어순과 표기 흔들림에 약합니다. "서울 리버사이드 호텔"과 "Riverside Hotel
  Seoul"은 같은 숙소여도 토큰이 하나도 겹치지 않아 후보로 잡히지 않습니다. 다국어 표기까지
  다루려면 정규화 사전이나 임베딩이 필요한데, 그건 이 저장소를 받은 사람이 그대로 돌릴 수
  없게 만드는 비용이라 넣지 않았습니다(판단 근거는 docs/ai-usage.md).
- 숙소 수가 늘면 비교 횟수가 제곱으로 늡니다. 지금은 숙소가 몇 개뿐이라 전수 비교로 충분하지만,
  수천 개가 되면 이름 앞글자나 지역으로 후보군을 먼저 좁히는 단계가 필요합니다.
